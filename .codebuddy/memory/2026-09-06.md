## LiveCalendar「List 视图自绘工具栏」的架构原因（用户确认过，勿误删）
- List 不是 FC 视图：FC v6 list 插件（@fullcalendar/list）原生只有「左时间+右标题」两列，`eventContent` 不支持自定义列头/列数，做不出「时间/新闻标题/国家/重要度」四列真表头 → List 用自绘组件 `LiveCalendarListView`，与 `<FullCalendar>` 平级。
- List 视图下 FC 被 `display:none` 整体隐藏（`cn(viewType === 'list' && 'hidden')`），FC 内置 headerToolbar 在其 DOM 子树内，会一起消失 → **必须自绘一份**，否则用户切进去无法导航、无法切回月/周/日（死胡同）。
- 自绘版刻意复用 FC 的 `.fc-toolbar` / `.fc-button-group` / `.fc-button` / `.fc-*-button` className，让 csscover 里 `[&_.fc-*]` 覆盖规则直接命中，视觉与月/周/日一致（不是另写样式）。
- 未采用「只隐藏 FC 视图区、保留其工具栏」：那样需把 List 的 `listRange` 反向 gotoDate 同步回 FC 才能修正标题、还要拦截 prev/next 语义、手写 active 态，且 FC datesSet 与 List onRangeChange 会互相触发（循环拉数）。现方案单一数据源 = `listRange`，FC 完全退场。

## `formatDate` 与 `toDateKey` 为何不合并（重要，防误改）
- 两者都取「浏览器本地时区的年/月/日」，但**契约不同，不可合并**：
  - `formatDate(value?: string|number|null)`：**展示用**。入参宽容（ISO 串 / 秒级 / 毫秒级时间戳 / null，走 `timestamp2data`），空值返回 `'—'`，非法值原样返回；输出 **斜杠** `"2026/09/05"`，依赖 `Intl('zh-CN')`。
  - `toDateKey(date: Date)`：**数据键用**。只收 `Date`，无容错（非法 Date 会得到 `"NaN-NaN-NaN"`，由调用方保证）；输出 **连字符** `"2026-09-05"`，不依赖 Intl、与 locale 无关。
- 结论：差异只在分隔符与容错，但分隔符是**用户可见的展示决定**。若强行把 formatDate 改成 `toDateKey(...).replace(/-/g,'/')`，会全站改变日期文案，属于 UI 变更而非重构 —— **不要做**，除非产品明确要统一日期展示格式。
- 附带发现（未处理）：`formatDate` / `formatTime` 硬编码 `'zh-CN'`，不支持项目已有的 zh-Hant / en 切换。
- 评估过「给 formatDate 加分隔符参数（'/' | '-'）以取代 toDateKey」：结论**否决**。
  - 技术可行（用 `Intl.formatToParts` 取年月日再按分隔符 join），但会让 toDateKey 的调用点获得「宽容语义」：null 会静默变成 `'—'` 并被当作 Map key / `<input type="date">` value，属于静默数据错误。
  - 关键区分：展示函数要**容错**（占位符/原样返回），数据键函数要**严格**（调用方保证）。两者不能合并。
  - 若将来确有「展示层要横杠」的需求，可行做法：`formatDate(value, { separator })` **只服务展示**，`toDateKey` 继续独立存在。

## 「List 工具栏 / handleListNav / handleViewChange 是否移入 ListView」评估结论
- **`handleViewChange` 无法整体搬走**（硬约束）：它写 `setViewType(next)`，而 `viewType === 'list'` 正是挂载 `LiveCalendarListView` 的条件 —— 组件不能拥有「卸载自己」的开关；且切回月/周/日要 `calendarRef.getApi().changeView()/updateSize()`，`calendarRef` 在 LiveCalendar。至少要拆成两半：「进入 List」分支由 FC 工具栏 List 按钮触发、留在 LiveCalendar；「切回 FC 视图」分支做成 `onViewChange` 回调下发给 ListView。
- **推荐方案 A（只搬展示层）**：工具栏 JSX + 标题计算 移入 `LiveCalendarListView`；`viewType`/`listRange`/`handleListNav`/`handleViewChange`/`weekRangeOf`/`shiftDays` 全部留在 LiveCalendar，通过新增 `onNavigate?(dir)` / `onViewChange?(next)` 两个 prop 下发。
  - 附带收益：`listTitle` 可由 ListView 用已有 `range` 自算 → 干掉 LiveCalendar 的 `listTitle`，`intlLocaleOf` 收回私有；工具栏的 `viewType === 'list'` 三元也可删（ListView 挂载条件本身即等价）。
  - 风险：低，不动状态与数据流。
- **不推荐方案 B（连 `listRange` 状态一起搬）**：会导致 `onRangeChange`（拉数契约）出现两个所有者（月/周/日走 FC `datesSet`、List 走 ListView）；且同步调用要改成 `useEffect`，拉数时机后移；`weekRangeOf` 会变成 LiveCalendar 反向从 ListView import。
